結論から言うと、この事案は高度な攻撃に敗れたというより、外部とつながる入口の脆弱性管理、認証、セキュリティ設定の例外、ベンダーとの責任分界が、いずれも十分に機能していなかったことが重なった事案として読めます。本記事では、2022年6月に公表された有識者会議の調査報告書をもとに、経緯と指摘を整理し、内部監査でどの統制をどんな証跡で確認するかを書きます。目的は公表された教訓を自社の監査に生かすことです。

## 事案の概要と復旧までの経緯

2021年10月31日の未明、病院内の複数のプリンタが一斉に犯行声明を印字し始め、事案が発覚しました。報告書によると、LockBit2.0によるランサムウェアに感染し、電子カルテの端末や関連サーバーのデータが暗号化されました。救急や新規患者の受け入れを止め、手術も可能な範囲で延期するなど、病院の機能は事実上停止しました。

侵入経路について、報告書は「思われる」「可能性が極めて高い」という表現を使っています。電子カルテ系で電子メールを使っていないこと、公開されたリモートデスクトップがなかったことなどを一つずつ検討し、残ったのが保守用のVPN装置でした。ただし、装置のログは復旧作業の中で保全されず、経路を証明するところまでは至っていません。この点は、事実と推定を分けて読む必要があります。

| 日付 | 主な出来事（報告書の記載に基づく） |
|---|---|
| 2021年10月31日 | 未明にプリンタから犯行声明が出力される。システム担当者が到着後、電子カルテのネットワークを遮断。午前8時にランサムウェア感染を確認し、警察へ相談。午前10時に災害対策本部を設置し、BCP（事業継続計画）に基づく対応を開始 |
| 11月3日 | VPN装置のファームウェアを更新。報告書は、VPNログの確認や保全が未確認だったと記している |
| 11月5日 | 調査・復旧のため、サーバーや端末を事業者へ発送 |
| 11月8日 | 修復を担う事業者との協議で、VPNを突破された可能性の指摘を受ける |
| 11月22日 | 身代金を支払わない方針を正式に決定。報告書によれば、身代金要求は最初のプリンタ出力のみ |
| 12月14日 | フォレンジック（デジタル証拠の調査）の結果報告で、7台の端末に不正アクセスの痕跡を確認 |
| 12月20日 | バックアップサーバーのデータが2018年以降物理的に削除されていたことを確認 |
| 12月29日 | 電子カルテのデータ復元を確認し、既存サーバーとレンタルサーバーを併用する構成での再稼働を決定 |
| 2022年1月4日 | 電子カルテを再稼働し、通常診療を再開 |

初動では、当直医の判断で救急受け入れを止め、早い段階で「災害相当」と判断してBCPを発動したことが、報告書でも評価されています。一方で、報告書は、サイバー攻撃への知識や経験が不足していたために初動に戸惑いがあったこと、関係する事業者の対応にも一貫性が欠けていたことを指摘しています。

## 報告書が指摘した原因

最初の原因は、VPN装置の脆弱性管理です。報告書によれば、保守用に設置されたVPN装置には、既知の脆弱性（CVE-2018-13379）が放置されていました。この脆弱性は、装置から管理者の認証情報を取得され得るものです。2021年9月にはこの種の装置の認証情報が世界で約8万7千台分公開され、調査では、その中に病院の情報が含まれていたことが確認されています。製造元は2019年から2021年にかけて繰り返し注意を呼びかけていましたが、利用側は対応していませんでした。さらに、接続元IPアドレスの制限や多要素認証もなく、認証情報があれば誰でも接続できる状態でした。

次に、侵入後の被害を広げた設定です。Active Directory（ユーザー認証や権限を一元管理する仕組み）では、パスワードの最小桁数が5桁、ログオン失敗時のロックアウトは無効、Administratorのアカウント名は未変更でした。ドメインユーザーが管理者グループに属していたため、攻撃者は高度な手法を使わなくても横展開（侵入した端末から他の端末やサーバーへ広げること）ができたと報告書は見ています。

三つ目は、アプリケーションの動作を優先してセキュリティを下げていたことです。電子カルテは古いブラウザ環境や、すでにサポートが終了した部品を前提とした設計でした。動作が不安定になるという理由で、Windows更新やアンチウイルスソフトが止められ、サーバーのファイアウォールも無効でした。**閉域網だから安全という前提のまま、設定の見直しも例外の承認も行われていなかったことが、被害の土台になっていました。**

四つ目は、組織と契約の問題です。報告書は、情報セキュリティのマネジメントシステムがなく、情報システムの担当が事実上1名だったことを挙げています。アプリケーションとインフラで別々の事業者と契約し、双方が責任は相手にあると認識していたため、設定や稼働後の保守の責任が宙に浮いていたとも書かれています。また、BCPは主に地震を想定しており、サイバー攻撃は想定外でした。

## 公表された改善の方向性

報告書の再発防止策は、組織面では、サイバー攻撃を含むリスクを継続的に見直す仕組み（マネジメントシステム）を持つこと、情報資産・設定・ログ・脆弱性対応状況を管理するセキュリティ・コントロールを整えること、適切な事業者を選定・管理すること、医療情報システム従事者のコミュニティをつくることが示されています。社会面では、ガイドラインの具体化なども課題とされました。

技術面の対策は、別冊の「技術編」にまとめられているとのことですが、本記事の執筆にあたっては確認していません。具体的な設定値は、各組織で最新の資料を確認してください。

## 内部監査の視点

ここからは、報告書の指摘に基づく一般論です。どの統制も、あれば確実に防げたと言えるものではありません。ただ、気づく機会を増やし、被害を小さくした可能性はあります。

1つ目は、外部から到達できる機器の棚卸です。VPN装置や保守用回線が資産台帳に載っているか、脆弱性情報を誰が受け取り、誰が適用を判断するかを確認します。保守をベンダーに任せている場合でも、委託契約に脆弱性の通知や適用が含まれているかを契約書で見ます。契約に含まれていなければ、誰も見ていない領域になります。

2つ目は、セキュリティ機能を止める例外の管理です。業務システムの都合で更新やウイルス対策を止めること自体は、現実にあり得ます。監査では、その判断が承認されているか、期限と代替策（接続制限、監視の強化など）があるかを見ます。承認のない恒久的な例外は、指摘事項になります。

3つ目は、認証と特権です。パスワード長、ロックアウト、標準アカウントの名前変更、日常利用のアカウントに管理者権限がないかを設定画面や出力結果で確かめます。詳しくは以前の記事「特権IDの監査で見るべき5つのポイント」も参考にしてください。認証情報の流出を知ったときに変更する手順があるかも、見落としがちな点です。

4つ目は、初動での証跡保全です。今回はファームウェア更新とシステム初期化の過程でログが残らず、原因を確認できませんでした。インシデント対応手順に「ログを保全してから復旧する」という順序と、フォレンジック事業者との契約や連絡先が含まれているかを確認します。

5つ目は、BCPの前提です。地震を想定した計画が初動で役立った点は、参考になります。そのうえで、サイバー攻撃で電子システムが長期間使えない場合の紙運用、外部委託先との連絡手段、復旧の優先順位まで訓練で試されているかを見ます。バックアップについては、以前の記事「バックアップ監査の進め方」の観点も使えます。

人員や予算の不足が背景にある場合は、不備の指摘にとどめず、リスクとして経営層に報告して判断を求めることも内部監査の役割です。

## 自社で確認すべき項目

| 確認項目 | 依頼する証跡 | よくある不備 |
|---|---|---|
| 外部接続機器の棚卸 | 外部から到達できる機器の一覧、保守用接続の一覧 | VPN装置や保守回線が台帳にない |
| 脆弱性情報の受領と対応 | 製造元・保守ベンダーからの通知、適用判断の記録 | 通知先が不明、適用の判断者がいない |
| VPN・管理画面の認証 | 接続元制限と多要素認証の設定画面、認証情報流出時の変更記録 | 認証情報だけで接続でき、流出後も変更していない |
| セキュリティ機能を止める例外 | 例外の承認記録、期限、代替策 | 承認も期限もなく、理由が引き継がれていない |
| ADのパスワードと権限 | グループポリシーの出力、管理者グループの所属一覧 | 桁数が短い、ロックアウトなし、日常利用の端末で管理者権限 |
| ベンダー間の責任分界 | 契約書、責任分担表、保守範囲の記載 | 構築と保守で契約が分かれ、境界が曖昧 |
| インシデント初動とBCP | 対応手順書、ログ保全の手順、サイバーを想定した訓練記録 | 地震想定のみ、ログ保全の手順がない |

明日からの行動として、まずは自社の外部接続点を一覧にして、それぞれの脆弱性情報の受け取り先と適用担当者を書き込んでみてください。空欄が見つかれば、そこが最初の監査テーマです。
