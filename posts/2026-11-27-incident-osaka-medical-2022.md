2022年10月31日に発生した大阪急性期・総合医療センターのランサムウェア被害は、調査委員会の報告書で、給食事業者のVPN機器から入られ、病院内の権限と認証の弱さで被害が広がったと整理されています。この記事では、報告書の指摘を内部監査の視点で読み替え、外部接続の管理、責任分界、特権・認証設定について「どこを見て、どんな証跡を依頼するか」を説明します。当事者を批判するのが目的ではありません。公表された教訓を、自社の監査計画に取り込むための読み方です。

## 事案の概要

調査委員会の報告書概要によると、2022年10月31日にサイバー攻撃で大規模なシステム障害が起き、電子カルテシステムが暗号化されました。そのため長期間の診療制限が必要になりました。基幹システムのサーバーが再稼働したのは障害発生から43日後、部門システムを含む全体の診療システムの復旧には73日かかりました。

診療への影響も資料に示されています。2022年11月の実績は、新入院患者数が558人（前年同月比33.3％）、初診患者数が465人（同17.9％）でした。被害額は、概要の時点では精査中とされ、調査・復旧費用が数億円以上、診療制限による逸失利益が十数億円以上と見込まれていました。個人情報の漏えいについては、通信ログとフォレンジック調査の結果から可能性は極めて低いとされつつ、調査は継続中と記載されています。

## 発生から復旧までの経緯

報告書の記載から、主な流れを整理します。時刻は資料の記載に従っています。

| 日付 | 出来事 |
|---|---|
| 2022年10月31日 早朝（4時台） | 給食事業者側のサーバーから、病院側の栄養給食管理サーバーへ大量のリモートデスクトップ（RDP）通信が発生（概要の構成図） |
| 同日 7時45分 | 病院が電子カルテの障害で問題を認知 |
| 同日 8時30分頃 | 調査でランサムウェア感染が確認される。電子カルテ関連のネットワークを遮断・利用停止し、紙のカルテ運用を開始 |
| 同日以降 | 厚生労働省から派遣された専門家チームが初動対応を支援 |
| 2022年12月12日 | 電子カルテを含む基幹システムが再稼働（障害発生後43日目） |
| 2023年1月11日 | 部門システムを含む診療システム全体が復旧（73日目） |
| 2023年3月28日 | 調査委員会が報告書と概要を公表 |

概要の構成図には、ログに関する注記もあります。VPN機器を10月31日夕方ごろにバージョンアップした結果、ログが消失し、更新前のバージョンは後日確認したという趣旨です。事後調査に必要な証拠の保全は、監査で見落とされやすい点です。

## 報告書が指摘した原因

報告書は、攻撃の流れを次のように推定しています。まず、情報基盤の構築事業者がリモート保守のために設置したVPN機器の脆弱性から、給食事業者の給食システムに侵入された。漏えいして公開されていたID・パスワードが使われた可能性もある、と併記されています。次に、給食事業者のデータセンターのID・パスワードが脆弱だったため、システム情報が窃取され、攻撃が広がりました。そこで得た病院サーバーの認証情報でRDP接続し、病院の給食サーバーに入り、ウイルス対策ソフトをアンインストールしました。さらにそこを踏み台に、電子カルテなどのサーバーへ広がりました。

原因は大きく四層で整理されています。

**技術面では、外部接続の管理不備と、内部のセキュリティ設定の弱さが重なったと指摘されています。** 外部接続については、VPN機器やファイアウォールの保守・脆弱性管理の役割分担が曖昧で、脆弱性が放置されていました。リモート保守を許可する基準も曖昧で、RDP接続は常時接続になっていました。接続元のセキュリティ環境の確認が不十分で、許可後に利用状況を確認していなかった点も挙げられています。

内部の設定では、次の四点が指摘されています。

- ユーザー全員に管理者権限が付与されていた。
- サーバーや端末のWindowsパスワードがすべて共通だった。
- アカウントロックアウトの設定がなかった。
- 電子カルテシステムのサーバーにウイルス対策ソフトが入っていなかった。

報告書は、侵入を許した場合でも初期設定が適切であれば、大規模な横展開は避けられた可能性があると述べています。

組織面では「ITガバナンスの欠如」が挙げられました。契約単位で保守や脆弱性管理の責任分界点が不明確でした。複数ベンダーが関わる契約でプロジェクト管理体制が曖昧でした。医療機器やリモート保守用機器、建築関係の情報システムが一元管理されていませんでした。ガイドラインの改定への追随も、組織的に確認されていませんでした。

人的な面では、「医療機関は閉域網だから安全」という誤った思い込み（閉域網神話）の中で、セキュリティ意識が薄れていたと指摘されています。概要の構成図には、検査・保守・機器監視などのための外部接続が十数か所あると示されています。閉域網と呼ばれていても、実際には外部と接続する経路があったことになります。

## 報告書の再発防止策と、その後の改善策

報告書の再発防止策は、原因に対応した内容です。

- 機器ごとに管理者と設置者の保守範囲・脆弱性管理の役割分担を、文書で確認する。
- 外部接続やリモート保守を許可する基準を定める。
- 許可の際は通信元のセキュリティ環境を確認する。
- 接続の目的や時間を確認し、通信ログを見て不正なアクセスの記録がないかを確認する。
- 一般ユーザーは標準ユーザー権限にする。
- パスワードを端末・サーバーごとに個別化する。
- アカウントロックアウトを有効にする。
- 電子カルテのサーバーにもウイルス対策ソフトを入れる。

組織面では、契約ごとに責任分界点と役割を文書化することが提案されています。具体的には、国の安全管理ガイドラインに基づくサービス仕様適合開示書とSLA（サービス品質の合意）を使う案です。診療情報系ネットワークにつながる機器とシステムを、すべて情報資産として洗い出してリスク分析することも提案されています。

病院を運営する大阪府立病院機構については、大阪府の資料に、同じ機構内のほかのセンターでの取り組みが載っています。外部接続する事業者への個別ヒアリング、外部接続に使うファイアウォールの脆弱性点検とバージョンアップ、電子カルテ等の端末でUSB機器を使えなくする制限などです。1か所で起きた事案を、組織全体の点検に広げた例といえます。

## 内部監査の視点：どこをどう見るか

ここからは、報告書の指摘に基づく一般論です。次に挙げる監査をしていれば必ず防げた、と断定するものではありません。ただ、報告書が挙げた弱点の多くは、設定値や台帳、契約書を確認すれば存在に気づけた性質のものです。

**外部接続は、「誰が、どの機器で、何の目的で、いつまで」を台帳で説明できるかを最初に確認します。** 外部接続の一覧を依頼し、実際のVPN機器・ファイアウォールの設定と突き合わせます。一覧が情報システム部門だけで作られ、施設管理や設備、医療機器の保守回線が漏れていないかも見ます。以前の記事で触れたクラウド責任共有モデルと同じで、委託先に任せる範囲と自社が持つ範囲を、契約書と運用の両方で確認します。

権限管理では、設定の実機確認が中心になります。以前の記事「特権IDの監査で見るべき5つのポイント」と「ユーザーアクセス権レビューの監査手続」で書いたとおり、規程があることと、設定が規程どおりであることは別です。管理者権限の保有者一覧、パスワード運用の設定、ロックアウトの設定、ウイルス対策の導入状況は、いずれもシステムから出力した画面や設定ファイルで確認できます。

| 確認項目 | 依頼する証跡 | よくある不備 |
|---|---|---|
| 外部接続の台帳と許可 | 外部接続一覧、許可申請書、接続元の確認記録、常時接続か都度接続かの区分 | 一覧にない回線が残っている。許可後に誰も利用状況を見ていない |
| 外部通信機器の脆弱性管理 | 機器台帳、実機のバージョン画面、パッチ適用履歴、保守契約書 | 台帳のバージョンと実機が違う。設置者と管理者の役割が書面にない |
| 管理者権限の付与状況 | ローカル管理者・ドメイン管理者の保有者一覧、付与の承認記録 | 業務上の必要がないのに全員が管理者。承認記録がない |
| パスワードとロックアウト | 認証ポリシーの設定出力、端末・サーバーでの共通パスワードの有無の確認結果 | 初期設定のまま共通化している。ロックアウトが未設定 |
| ウイルス対策などの導入範囲 | 導入状況の一覧を資産台帳と突き合わせた結果、除外サーバーの例外承認書 | 重要なサーバーほど「影響が怖い」として除外されたまま |
| ログの保全 | ログの保存期間設定、機器更新前のログ退避手順 | 機器更新や再起動で、調査に必要なログが失われる |
| 委託先・資産の把握 | 契約書の責任分界の記載、情報資産台帳（設備・医療機器・保守用機器を含む） | 契約単位で管理され、全体を見ている人がいない |

委託先管理も重要です。報告書によれば、病院側のシステムと給食事業者側のシステムは、同じ構築事業者・アプリ提供事業者が関わっていました。侵入された給食事業者側のデータセンターにも弱いID・パスワードがありました。委託先の統制が弱ければ、自社の統制だけでは守りきれません。委託先の第三者保証報告書の読み方は、以前の記事「SOC1・SOC2報告書の読み方」を参照してください。報告書がない小規模な委託先には、アンケートだけで済ませず、接続を許可する条件（多要素認証、接続時間の限定、ログ提出）を契約や運用に入れられているかを見るのが現実的です。

最後に、復旧の観点です。今回は基幹システムの再稼働に43日かかりました。バックアップの有無だけでなく、復元の手順と所要時間まで確かめる必要があります。これは以前の記事「バックアップ監査の進め方」で扱った論点です。同じ種類の事案として、以前の記事「つるぎ町立半田病院のランサムウェア被害を内部監査の視点で読む」も参考になります。

## 自社で確認すべき項目

自社の監査計画やセルフチェックに使える質問を、表にまとめます。

| 質問 | 確認先・証跡 |
|---|---|
| 委託先や保守業者が使う外部接続を、すべて一覧にできるか | 情報システム部門、施設・設備部門、各業務部門への照会結果 |
| 外部通信機器の脆弱性対応は、設置者と管理者のどちらが行うか、書面で決まっているか | 契約書、保守仕様書、責任分界の文書 |
| リモート保守は常時接続か、必要なときだけ開ける方式か | 機器の設定、接続ログ |
| 一般ユーザーが管理者権限を持っていないか | 管理者グループのメンバー一覧 |
| サーバーや端末で、同じパスワードが共通になっていないか | 運用手順書と、設定の実機確認結果 |
| アカウントロックアウトは有効か | 認証ポリシーの設定出力 |
| 重要なサーバーを含め、ウイルス対策などの導入範囲に例外がないか | 導入状況一覧、例外承認書 |
| 機器更新の前に、ログを退避する手順があるか | 変更手順書、更新時の作業記録 |

明日からの実務では、次の三つから始めるのが現実的です。第一に、外部接続の一覧を依頼し、実機の設定と突き合わせる。第二に、管理者権限の保有者一覧と、パスワード・ロックアウトの設定出力を取り寄せる。第三に、主要な委託先との契約書で、保守範囲と脆弱性対応の責任がどこに書かれているかを確かめる。なお、報告書が参照しているガイドラインの版や、国の関連規程は改定されることがあります。実際の確認では、最新の版を参照してください。
